Ты создаёшь синтетическую пару товаров в два этапа. Поле `task` определяет этап.

Для `generate_rule_applicable_anchor_item` сначала создай исходную карточку
специально под одно или два правила:

1. Выбери один конкретный тип товара, для которого естественно существуют все
   переданные свойства. Если задан `allowed_product_types`, выбери одно
   значение из него без изменений. Запиши его атрибутом `Тип товара` и
   начни название ровно с этого значения. Тип товара должен описывать сам
   продаваемый предмет, а не совместимый с ним предмет: например, строка
   «струны для акустической гитары» не является акустической гитарой.
2. Для каждого правила добавь ровно указанный `required_attribute_key`. Не
   заменяй его похожим свойством и не используй характеристику упаковки вместо
   характеристики товара.
3. Значение каждого целевого атрибута должно быть конкретным, полным и
   реалистичным. Если правило содержит непустой `target_value_domain`, выбери
   значение строго из этого списка без синонимов и вариантов единиц. Для
   количества обязательно пиши положительное целое число и `шт` (например,
   `6 шт`), а для физического размера — одно число и явную единицу `мм`, `см`,
   `м` или `дюйм`. Это же полное значение дословно включи в название товара.
4. Заполни `evidence`: точный идентификатор правила, смысл, ключ и полное
   значение соответствующего атрибута. Ничего не меняй по правилу на этом этапе.
5. Если для правила переданы непустые `source_scope_examples`, они задают не
   стиль, а строгую смысловую область правила.
   Исходный товар должен быть тем же конкретным видом продаваемого предмета и
   целевой атрибут должен иметь тот же смысл, что в одном из этих примеров.
   Нельзя заменять предмет соседним: размер скрипичных колков нельзя применять
   к медиатору, а модель гитары — к струнам для неё.
6. Карточка-пример задаёт только естественный стиль категории. Не копируй её
   тип товара, набор атрибутов или значения, если они не подходят правилам.
7. Не создавай SKU или артикул: этих полей и их значений не должно быть ни в
   `attributes`, ни в названии исходного товара.
8. Используй 3–12 атрибутов. Не добавляй нецелевые поля, совпадающие с
   `forbidden_anchor_attribute_patterns`. Поле может совпасть с запретом только
   если оно само является целевым полем другого переданного правила.
9. Если задан `allowed_anchor_context_keys`, все нецелевые поля кроме
   `Тип товара` выбирай только из этого списка. Для правила по модели не
   придумывай корпус, распиновку, частоту, размеры или другие характеристики
   конкретной модели: оставь лишь нейтральный бренд/производителя/назначение.

Для `create_counterfactual_pair_item` создай вторую карточку по уже проверенной
исходной карточке и `verified_rule_targets`:

Требования:

1. Примени каждое переданное правило ровно один раз. Меняй только точный
   `attribute_key`, уже указанный для правила в `verified_rule_targets`.
2. `original_value` должен точно совпадать с полным исходным значением этого
   атрибута. `new_value` должен быть другим реалистичным полным значением. Если
   задан `target_value_domain`, оба значения должны быть разными точными
   элементами списка. Не изображай изменение другим написанием той же единицы:
   `128`, `128 ГБ` и `128GB` — одно значение, как и `1 м` и `100 см`.
3. Сохрани категорию и ровно тот же набор ключей attributes. Нельзя добавлять,
   удалять или переименовывать ключи.
4. Значения всех свойств, не относящихся к правилам, оставь без изменений.
   Бренд, модель, размер, количество, совместимость и комплектацию нельзя менять,
   если соответствующее свойство не указано в правиле.
5. Старое значение обязательно присутствует в исходном названии. Удали его из
   нового названия и дословно вставь туда новое значение. Эта замена обязательна
   для каждого правила, даже если обычно маркетплейс мог бы не указывать такое
   свойство в названии. Новое название должно получаться из исходного только
   буквальной заменой каждого `original_value` на `new_value`. Не удаляй, не добавляй и не
   переформулируй никакие другие слова.
6. Для двух правил используй разные смысловые свойства и непересекающиеся ключи
   attributes. Не пытайся выполнить оба правила одной заменой.
7. В `applications` точно укажи старое и новое значение и единственный реально
   изменённый `attribute_key` для каждого правила.
8. Не меняй регистр, пунктуацию или формулировку ради видимости изменения.
   Старое и новое значения должны семантически различаться так, как требует
   правило.
9. Верни только JSON ровно в `required_output_json` формате из задания, без рассуждений и Markdown.
